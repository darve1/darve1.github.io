## 개요

스택 버퍼 오버플로우 취약점을 이용하면 스택의 반환 주소(Return Address)를 조작해 실행 흐름을 획득할 수 있습니다. 이번 글에서는 이런 공격으로부터 반환 주소를 보호하는 스택 카나리(Stack Canary)에 대해 알아봅시다.

## 스택 버퍼 오버플로우

스택 카나리를 알아보기 전에 먼저 스택 버퍼 오버플로우를 설명하겠습니다. 이름에 버퍼와 오버플로우가 들어간다는 점에서 유추할 수 있듯이, 특정 크기의 메모리(버퍼)에 그보다 많은 데이터가 저장되면 데이터가 버퍼를 넘쳐 다른 메모리 공간의 데이터를 오염시킬 수 있는 취약점입니다.

이것이 스택에서 일어나는 것을 스택 버퍼 오버플로우(Stack Buffer Overflow)라고 합니다.

## 스택 카나리 원리

스택 카나리는 함수의 프롤로그에서 스택 버퍼와 반환 주소 사이에 임의의 값을 삽입하고, 함수의 에필로그에서 해당 값의 변조 여부를 확인하는 보호 기법입니다.

![스택 카나리 적용 전후의 스택 구조](assets/posts/2026-11-05-stack-canary/image-20261105-141209.png)
_출처: [she11.tistory.com](https://she11.tistory.com/130)_

카나리는 32비트 아키텍처에서는 4바이트, 64비트 아키텍처에서는 8바이트 크기이며, 스택 버퍼와 SFP(Saved Frame Pointer, 이전 스택 프레임의 rbp) 사이에 위치합니다.

그래서 스택 버퍼 오버플로우로 반환 주소를 덮으려면 넘친 데이터가 반드시 카나리를 지나가야 합니다. 이때 카나리 값을 모르고 반환 주소를 덮었다면, 반환 주소뿐만 아니라 카나리 값도 바뀌게 됩니다. 이 경우 에필로그에서 변조가 확인되어 프로세스가 강제 종료되기 때문에 공격자는 실행 흐름을 획득하지 못합니다.

## 직접 확인해 보기

> [!info] 실습 환경
> Ubuntu 24.04 (WSL2, x86_64), gcc 13.3.0, glibc 2.39, gdb 15.1 + pwndbg

Dreamhack의 예제 코드를 직접 컴파일하고 실행해 보았습니다.

```c
// Name: canary.c

#include <unistd.h>

int main() {
  char buf[8];
  read(0, buf, 32);
  return 0;
}
```
_출처: [Dreamhack](https://dreamhack.io/)_

위 코드는 크기가 8바이트인 `buf` 배열을 만드는데, `read`로 최대 32바이트까지 입력받기 때문에 남는 24바이트가 `buf` 뒤의 메모리를 덮게 됩니다. 카나리가 적용된 경우 스택은 다음과 같이 덮입니다.

```text
[ buf    8B ]  ← 입력 0~7바이트
[ canary 8B ]  ← 8~15바이트가 카나리를 덮음
[ SFP    8B ]  ← 16~23바이트
[ RET    8B ]  ← 24~31바이트, 반환 주소까지 덮음
```

즉, 반환 주소까지 덮을 수 있는 스택 버퍼 오버플로우 취약점이 존재합니다.

### 카나리 비활성화

스택 버퍼 오버플로우가 일어나는지 확인하기 위해 코드를 실행하기 전에 알아 둘 점이 있습니다. Ubuntu의 gcc는 기본적으로 `-fstack-protector-strong` 옵션이 적용되어 있어, 별도 옵션 없이 컴파일해도 배열 같은 지역 버퍼가 있는 함수에는 스택 카나리가 삽입됩니다. 그래서 카나리를 끄려면 `-fno-stack-protector` 옵션을 사용해야 합니다.

![카나리를 끄고 컴파일한 뒤 실행](assets/posts/2026-11-05-stack-canary/image-20261105-143323.png)

컴파일할 때부터 gcc가 크기 8인 버퍼에 32바이트를 쓴다는 경고(`-Wstringop-overflow`)를 띄워 줍니다. 실행해서 긴 입력을 넣으면 실제로 반환 주소가 덮여서 `Segmentation fault`가 뜨는 것을 볼 수 있습니다.

### 카나리 활성화

이번에는 옵션 없이 컴파일하고 코드를 실행해 보겠습니다.

![옵션 없이 컴파일한 뒤 실행](assets/posts/2026-11-05-stack-canary/image-20261105-143715.png)

이번에는 `Segmentation fault`가 아니라 `stack smashing detected`와 `Aborted`라는 에러가 발생합니다. 이는 스택 버퍼 오버플로우가 탐지되어 프로세스가 강제 종료되었음을 의미합니다.

### 디스어셈블 비교

![no_canary의 main 디스어셈블](assets/posts/2026-11-05-stack-canary/image-20261105-144014.png)
_no_canary_

![canary의 main 디스어셈블](assets/posts/2026-11-05-stack-canary/image-20261105-143944.png)
_canary_

no_canary와 canary의 디스어셈블을 비교하면, canary에는 main 함수의 프롤로그와 에필로그에 각각 다음 코드가 추가되었습니다.

```text
; 프롤로그
0x0000000000001175 <+12>:    mov    rax,QWORD PTR fs:0x28
0x000000000000117e <+21>:    mov    QWORD PTR [rbp-0x8],rax
0x0000000000001182 <+25>:    xor    eax,eax

; 에필로그
0x000000000000119f <+54>:    mov    rdx,QWORD PTR [rbp-0x8]
0x00000000000011a3 <+58>:    sub    rdx,QWORD PTR fs:0x28
0x00000000000011ac <+67>:    je     0x11b3 <main+74>
0x00000000000011ae <+69>:    call   0x1060 <__stack_chk_fail@plt>
```

**프롤로그**는 순서대로 다음을 실행합니다.

1. `+12`: `fs:0x28`의 값 8바이트를 가져와 `rax`에 넣습니다. `fs:0x28`에는 프로그램이 시작할 때 커널이 준 랜덤 값으로 정해진 카나리 원본이 들어 있어서, 공격자는 카나리 값을 알 수 없습니다.
2. `+21`: 그 값을 스택의 `rbp-0x8`, 즉 카나리 위치에 저장합니다.
3. `+25`: `xor eax, eax`는 같은 값끼리 xor하기 때문에 `rax`에 0이 저장됩니다. 카나리 값이 레지스터에 남지 않도록 지우는 것입니다.

**에필로그**는 순서대로 다음을 실행합니다.

1. `+54`: 스택에 있던 카나리를 `rdx`로 꺼냅니다.
2. `+58`: 원본 값(`fs:0x28`)을 빼서 변조되었는지 확인합니다. 두 값이 같으면 결과가 0입니다.
3. `+67`: 결과가 0이면 `main+74`로 점프해 `leave; ret`을 실행하고 정상적으로 반환합니다.
4. `+69`: 값이 다르다면 `__stack_chk_fail`을 호출해 `stack smashing detected`를 출력한 뒤 강제 종료합니다.

## 정리

- 스택 카나리는 스택 버퍼와 SFP 사이에 랜덤 값을 넣고, 함수가 반환하기 전에 그 값이 바뀌었는지 확인해 반환 주소를 보호하는 기법입니다.
- 카나리 원본은 `fs:0x28`에 있고, 프롤로그에서 스택에 복사한 뒤 에필로그에서 원본과 비교합니다.
- 카나리가 바뀌었으면 `__stack_chk_fail`이 프로세스를 종료하기 때문에, 덮어쓴 반환 주소로 실행 흐름이 넘어가지 않습니다.
- Ubuntu의 gcc는 카나리가 기본으로 켜져 있고, `-fno-stack-protector` 옵션으로 끌 수 있습니다.
