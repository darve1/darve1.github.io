## 개요

IEEE S&P 2025에 실린 논문 "The File That Contained the Keys Has Been Removed: An Empirical Analysis of Secret Leaks in Cloud Buckets and Responsible Disclosure Outcomes"를 읽고 정리해 보았습니다.

공개로 잘못 설정된 클라우드 버킷에서 실제로 쓸 수 있는 키가 얼마나 새고 있는지 측정한 논문입니다. 그리고 이를 주인에게 알렸을 때 어떻게 대응하는지까지 추적했습니다.

> [!info] 논문 정보
> Soufian El Yadmani, Olga Gadyatskaya (Leiden University), Yury Zhauniarovich (TU Delft)
> 2025 IEEE Symposium on Security and Privacy, pp. 3180-3198, [DOI 10.1109/SP61157.2025.00009](https://doi.org/10.1109/SP61157.2025.00009)
> 원문은 [TU Delft 저장소](https://repository.tudelft.nl/record/uuid:c54c9272-7220-448c-a7b8-f82124fea579)에서 볼 수 있습니다.

## 읽기 전에 정리한 것

최근에는 애플리케이션을 저장하고 배포할 때 클라우드 서비스를 사용하는 경우가 많아졌습니다. 그만큼 클라우드 보안도 중요한 문제가 되고 있습니다.

논문 제목에 나온 클라우드 버킷은 클라우드 저장소에서 파일에 해당하는 객체들을 담는 저장 단위입니다. 이 논문은 이 버킷이 공개로 잘못 설정되어 있을 때, 그 안에 올라간 설정 파일 속 API 키나 비밀번호가 외부에 노출되는 문제를 다룹니다.

이 문제가 치명적인 이유는 키가 곧 시스템 접근 권한이기 때문입니다. 버킷 안의 사진이나 문서가 새는 것도 문제지만, AWS 키가 새면 공격자는 그 키로 다른 버킷의 데이터를 가져가거나, 서버를 띄우거나, 권한을 바꿀 수 있습니다.

지난 수년 동안 비밀 정보 유출 문제는 점점 심각해졌고, 잘못 설정된 클라우드 버킷에서 비밀 정보가 새는 사례도 연구자들이 보고해 왔습니다. 하지만 버킷 속 비밀 정보가 얼마나 새고 있는지 실질적으로 버킷을 뒤져서 노출된 키를 측정하려는 연구는 지금까지 없었습니다.

## 논문이 등장한 배경

### 비밀 정보는 어디로 새는가

요즘 애플리케이션은 결제, 메일 발송, 파일 저장 같은 기능을 직접 만들지 않고 외부 서비스를 가져다 씁니다. 이런 서비스는 API 키나 토큰으로 접근을 제한하는데, 개발자가 이 키를 설정 파일에 그대로 적어 두고 그 파일이 외부에 공개되는 일이 자주 일어납니다.

논문은 도입부에서 토요타 사례를 듭니다. 공개 GitHub 저장소에 데이터베이스 접근 키가 올라가 있었고, 이 키가 2017년 12월부터 2022년 9월까지 약 5년 동안 노출되어 고객 29만 6,019명의 정보에 접근할 수 있는 상태였습니다. 업계 조사로는 유출된 키의 74%가 끝내 폐기되지 않는다고 합니다.

비밀 정보 유출 문제가 심각해지면서 GitHub는 코드에서 비밀 정보를 자동으로 탐지하는 서비스를 제공하며, 최근에는 비밀 정보 유출을 막기 위해 모든 푸시 작업에 이 기능을 활성화했다고 합니다. 하지만 모든 유출을 막은 것은 아니라고 합니다.

### 공개된 클라우드 버킷

버킷의 접근 권한을 공개로 잘못 설정하면 주소만 알면 누구나 안의 파일을 내려받을 수 있습니다. 이런 공개 버킷을 모아서 검색할 수 있게 해 주는 GrayhatWarfare라는 사이트도 있어서, 공격자는 버킷을 직접 찾지 않고 검색만 해도 됩니다. 연구자가 일부러 열어 둔 버킷을 공격자가 몇 시간 만에 찾아냈다는 실험 결과도 있습니다.

저자들은 이 상황에서 두 가지를 묻습니다. 공개 버킷에 실제로 쓸 수 있는 키가 얼마나 있는지, 그리고 주인에게 신고하면 제대로 고치는지입니다.

## 저자들의 접근 방식

### 핵심 아이디어

이 논문은 실제로 사용 가능한 키만 세었습니다. 키처럼 생긴 문자열을 찾기만 하면 이미 폐기된 키나 예시로 적어 둔 키까지 잔뜩 걸릴 겁니다. 그래서 저자들은 찾은 키를 실제 서비스에 보내 지금도 쓸 수 있는지 확인한 뒤에 쓸 수 있는 것만 결과에 넣었습니다.

이때 확인하는 과정이 서비스에 피해를 주면 안 되기 때문에 읽기만 하는 요청으로 확인할 수 있는 키 종류만 골랐습니다. 이렇게 하면 가짜 키는 섞이지 않지만, 이미 폐기된 키나 확인할 수 없는 종류의 키는 빠집니다. 그래서 논문은 이 숫자를 실제 유출의 최소치로 봅니다.

### 데이터 살펴보기

저자들은 먼저 GrayhatWarfare가 2024년 1월 19일에 공개한 데이터를 살펴보았습니다. 이 시점에 AWS, Google Cloud, Azure, DigitalOcean 네 곳의 공개 버킷은 45만 3,296개였고, 그중 AWS가 31만 6,180개(69.75%)로 가장 많았습니다. 그 뒤로 Google Cloud, Azure, DigitalOcean 순이었습니다.

표본으로 뽑은 버킷 1,600개(클라우드마다 400개)에는 버킷 하나에 파일이 평균 6천~1만 6천 개씩 들어 있었습니다. 가장 많은 것은 jpg, png 같은 이미지 파일이었습니다. 이걸 전부 내려받아 볼 수는 없어서, 키가 들어 있을 만한 파일만 골라서 보기로 했습니다.

### 분석 과정

논문의 분석 과정은 순서대로 다음과 같습니다.

1. 파일 고르기: `.env`, `.config`, `.json`, `.yml`, `.sh`처럼 키가 적혀 있을 만한 설정 파일과 코드 파일 10종을 검색합니다. 100MB보다 큰 파일은 뺐습니다.
2. 내려받기: 검색으로 나온 파일을 내려받습니다. 2024년 2월 7일부터 3월 26일까지 48일이 걸렸다고 합니다.
3. 키 찾기: AWS, Google Cloud, Slack, GitHub 같은 서비스 25종의 키 형식을 정규식으로 찾습니다.
4. 확인하기: 찾은 키로 읽기만 하는 요청을 보내고, 돌아온 응답으로 지금도 쓸 수 있는 키인지 판단합니다.
5. 신고하기: 파일 안의 이메일이나 회사 이름을 단서로 주인을 찾아 이메일로 알립니다.
6. 추적하기: 신고한 뒤에도 버킷, 파일, 키 상태를 계속 확인해서 주인이 무엇을 고쳤는지 기록합니다.

신고할 때는 네덜란드의 비영리 보안 대응 조직이 함께했습니다. 개인 연구자보다 이름 있는 조직이 보낸 알림을 더 믿고 빨리 대응한다는 기존 연구가 있었기 때문입니다.

## 결과와 드러난 한계

### 얼마나 새고 있었나

고른 10종의 파일은 906만 8,672개였고, 중복을 빼면 534만 3,257개였습니다. 이 중 192개 파일에서 실제로 쓸 수 있는 키 215개가 나왔습니다. 파일 수에 비하면 매우 적은 수의 유출(고유 파일의 0.0036%)이지만, 하나하나가 회사 시스템에 접근할 수 있는 키였습니다. 키가 나온 파일에는 평균 1.12개씩 들어 있어서, 파일 하나에 키를 여러 개 적어 두는 경우도 많았습니다.

종류별로는 AWS 키가 100개로 가장 많았습니다. 그다음이 Google Cloud 키 32개, Slack 키 15개였고, 메일 발송 서비스 두 곳의 키가 각각 14개와 13개였습니다.

파일 종류별로 보면 키가 나온 파일 수는 `.yml`과 `.py`가 37개, `.sh`가 34개, `.json`이 33개로 많았습니다. 하지만 파일 하나에서 키가 나올 확률은 `.env`가 0.44%로 가장 높았고 `.config`가 0.098%, `.sh`가 0.086%로 뒤를 이었습니다. 제가 공격자여도 `.env` 파일부터 찾아볼 것 같습니다.

저자들은 놓친 키도 확인해 보았습니다. 클라우드마다 100개씩 뽑은 버킷 400개의 파일을 종류와 상관없이 전부 검사했더니, 암호가 걸리지 않은 압축 파일에서 Slack 키 1개가 나왔습니다. Azure 설정 파일에서도 키가 나와서 같은 종류의 파일 260개를 따로 검사하자 쓸 수 있는 키가 3개 더 나왔습니다.

### 사례

가장 심각했던 사례는 어느 회사가 쓰던 CrowdStrike 보안 솔루션의 API 키였습니다. 이 키가 있으면 그 회사의 보안 설정을 바꾸고 계정을 추가할 수 있어서, 보안 기능을 끄고 들키지 않게 공격할 수도 있었습니다. 이 회사는 신고 하루 안에 파일을 지우고 키를 폐기했습니다.

정부 기관의 버킷에서는 다른 버킷 230개에 접근할 수 있는 AWS 키가 나왔습니다. 2024년 4월 15일에 신고를 받은 기관은 다음 날인 4월 16일에 키가 든 파일에 접근하지 못하게 막았습니다. 하지만 키는 폐기하지 않았고, 6일 뒤인 4월 22일에 같은 파일이 다시 공개 상태로 올라왔습니다. 저자들은 배포 파이프라인이 잘못된 권한으로 파일을 자동으로 올리고 있었을 것이라고 봅니다. 다시 신고를 받고 나서도 기관은 파일만 다시 막았고 키는 끝내 폐기하지 않았습니다.

메일 발송 서비스의 키 13개는 그 회사 이름으로 피싱 메일을 보낼 수 있는 키였습니다. 한 회사는 정말 가능한지 증명해 달라고 해서, 연구팀이 그 회사 보안팀 주소로 시험 메일을 한 통 보내 보였습니다. 결국 13개 중 12개가 폐기되었습니다.

### 신고하면 고치는가

저자들은 키 215개 중 160건의 주인을 찾아 직접 신고했습니다. 주인을 찾지 못해 클라우드 회사에 넘긴 것이 50건, 신고하기 전에 이미 해결된 것이 5건이었습니다. 클라우드 회사 중 답장을 한 곳은 Amazon뿐이었고, 그마저도 고객이 직접 고칠 문제라는 답이었습니다.

관찰 기간은 신고를 시작한 2024년 4월 15일부터 9월 15일까지 5개월이었습니다. 직접 신고한 160건 중 95건(59.37%)은 조치가 있었고 65건(40.62%)은 아무 조치도 없었습니다. 답장을 보낸 곳은 20곳뿐이었고 나머지는 말없이 고쳤습니다. 개인정보 처리방침 페이지에 적힌 이메일로 연락한 11곳 중에서는 9곳이 문제를 고쳤습니다.

제가 보기에는 속도가 꽤 빨랐습니다. 26건(16.25%)이 신고 하루 안에, 28건(17.5%)이 그다음 날 고쳐져서 160건 중 33.75%가 신고 다음 날까지 해결되었습니다. 20일이 지나서 뒤늦게 고쳐진 것도 28건(17.5%)이었습니다.

제대로 해결하기 위해서는 버킷 막기, 파일 막기, 키 폐기를 모두 해야 합니다. 논문에 적힌 조치가 있었던 95건을 방법별로 나누면 다음과 같습니다.

1. 세 가지 모두: 19건
2. 파일 막기와 키 폐기: 18건
3. 키 폐기만: 33건
4. 파일 막기만: 19건
5. 버킷과 파일만 막고 키는 그대로: 6건

키를 폐기하지 않은 25건은 누군가 이미 파일을 내려받았다면 여전히 위험합니다. 논문은 키가 여러 시스템에 들어가 있어서 바로 폐기하면 서비스가 멈출 수 있기 때문에, 일단 접근만 막는 쪽을 고른 것으로 봅니다.

### 저자가 밝힌 한계

논문에서 직접 밝힌 한계는 다음과 같습니다.

1. 데이터가 GrayhatWarfare 한 곳에서만 나왔습니다. 이 사이트가 전체 공개 버킷을 얼마나 대표하는지 알 수 없고, 이런 사이트의 유료 이용권을 산 것도 윤리적으로 문제가 될 수 있습니다.
2. 확인할 수 있는 키 25종과 파일 10종만 봤기 때문에 놓친 키가 많을 것입니다. 압축 파일과 Azure 설정 파일에서 키가 더 나온 것이 그 예이고, 다음 연구에서는 이런 파일도 봐야 한다고 덧붙입니다.
3. 데이터 시점(1월 19일)부터 신고를 시작하기(4월 15일)까지 약 3개월이 걸렸습니다. 공격자가 몇 시간 만에 버킷을 찾는다는 점을 생각하면, 그사이 키가 이미 악용되었을 수 있습니다.
4. 아무 조치가 없던 65건(40.62%)이 왜 그랬는지는 알 수 없었습니다. 메일이 스팸으로 갔거나, 버려진 버킷이거나, 일부러 열어 둔 버킷일 수 있다고 봅니다.

또한 2024년 1월 19일 시점이기에 시간이 지나며 유출이 늘었는지 줄었는지는 알 수 없습니다.

## 느낀 점과 앞으로 할 것

### 느낀 점

가장 인상 깊었던 것은 유출된 키의 개수보다 고친 방식이었습니다. 59%가 조치를 했지만 세 가지를 모두 한 곳은 19건뿐이었고, 파일만 숨기고 키는 그대로 둔 곳도 있었습니다. 파일을 숨기면 더 새는 것만 막을 수 있고, 이미 샌 키를 못 쓰게 하려면 폐기해야 합니다.

정부 기관 사례도 기억에 남습니다. 사람이 파일을 막아도 배포 파이프라인이 다시 공개 권한으로 올려 버리면 소용이 없습니다. 이 사례를 보고 파일을 막는 것과 함께 배포 파이프라인도 고쳐야 한다는 것을 알게 되었습니다.

AWS는 2023년 4월부터 새로 만드는 버킷의 공개 접근을 기본으로 막고 있습니다. 그런데도 공개 버킷이 여전히 많았던 것을 보면, 기본 설정을 안전하게 바꿔도 예전에 만든 버킷이나 사람이 직접 바꾼 설정까지 막지는 못하는 것 같습니다.

### 더 읽어볼 논문

이어서 읽어 보고 싶은 논문은 다음과 같습니다.

1. Meli 외, "How Bad Can It Git? Characterizing Secret Leakage in Public GitHub Repositories" (NDSS 2019) - 공개 GitHub 저장소에서 키가 노출되는 규모를 측정한 연구입니다. 이 논문이 한 일을 GitHub에서 한 것이라서 비교해 보고 싶습니다.
2. Li 외, "You've Got Vulnerability: Exploring Effective Vulnerability Notifications" (USENIX Security 2016): 취약점을 어떻게 알려줘야 실제로 고치는지 실험한 연구입니다. 이 논문이 보안 대응 조직과 함께 신고한 근거로 든 연구 중 하나입니다.

### 다른 분야에 적용해 볼 가능성

같은 방법은 누구나 파일을 올리고 받을 수 있는 공개 서비스라면 어디든 적용할 수 있을 것 같습니다. Docker Hub의 공개 이미지, npm과 PyPI 패키지, Hugging Face에 올라간 모델과 예제 코드에도 `.env`나 설정 파일이 섞여 올라가는 일이 있습니다.

또 이 논문은 해외 클라우드 네 곳만 다뤘습니다. 신고한 160건 중 한국이 7건으로 여섯 번째로 많았는데, 현재 국내 클라우드 저장소에서는 어떤지 궁금합니다.

### 직접 재현해 보고 싶은 것

남의 버킷을 허락 없이 뒤질 수는 없기 때문에, 제 AWS 계정 안에서 작게 따라 해 보려고 합니다.

1. 버킷 하나를 공개로 만들고, 이미 폐기한 키를 넣은 `.env` 파일과 평범한 파일을 섞어 올립니다.
2. 논문에 실린 정규식 몇 개로 파일을 검사하는 스크립트를 짜서 키를 찾아봅니다.
3. 찾은 키가 지금도 쓸 수 있는지 읽기만 하는 요청으로 확인합니다. 살아 있는 키는 공개 버킷에 올리지 않고 제 컴퓨터에서만 응답을 비교합니다.
4. 정부 기관 사례처럼 배포 파이프라인이 같은 파일을 공개 권한으로 다시 올리는 상황을 만들고, 버킷의 공개 접근 차단 설정을 켜면 막히는지 확인합니다.

### 연구나 프로젝트로 발전시킨다면

논문에서 아쉬웠던 것은 2024년만 봤다는 점과, 주인들이 고친 방식이 불완전했다는 점입니다. 그래서 제가 발전시킨다면 조직의 버킷을 계속 감시하다가 유출을 찾으면 버킷 막기, 파일 막기, 키 폐기를 모두 했는지 확인해 주는 도구를 만들어 보고 싶습니다.

정부 기관 사례처럼 배포할 때마다 다시 공개되는 문제를 잡으려면, 배포 파이프라인에서 파일을 올리기 전에 키가 들어 있는지 검사하는 단계도 필요할 것 같습니다.
