## 개요

No-eXecute(NX)는 메모리 페이지마다 명령어를 실행할 수 있는지를 구분하는 보호 기법입니다. 인텔에서는 XD, AMD에서는 NX, 윈도우에서는 DEP, ARM에서는 XN이라고 부르는데, 이름만 다를 뿐 모두 같은 보호 기법입니다.

이번 글에서는 NX가 어떤 공격을 막는지 알아보고, NX를 켰을 때와 껐을 때의 차이를 직접 확인해 봅시다.

## 메모리 영역과 권한

메모리 페이지(Page)는 운영체제가 프로세스의 가상 메모리를 일정한 크기로 나누어 관리하는 단위입니다. 페이지마다 읽기(r), 쓰기(w), 실행(x) 권한을 따로 설정할 수 있고, **CPU는 명령어를 실행할 때마다 그 페이지에 실행 권한이 있는지 확인합니다.**

프로세스의 가상 메모리는 용도에 따라 여러 영역으로 나뉘고, 각 영역에는 필요한 권한만 주어집니다.

![메모리 영역별 용도와 권한](assets/posts/2026-11-12-nx/memory-permissions.png)

그림을 보면 쓰기 권한(`w`)과 실행 권한(`x`)을 함께 가진 영역이 하나도 없습니다. 명령어가 들어 있는 코드 영역은 실행만 되고, 데이터가 들어 있는 나머지 영역은 실행되지 않습니다.

## NX 원리

쓰기 권한과 실행 권한을 한 영역에 같이 주지 않는 이유는 다음과 같습니다.

- 코드 영역에 쓰기 권한이 있으면, 취약점으로 원하는 주소에 값을 쓸 수 있는 공격자가 원래 있던 명령어를 자기가 원하는 코드로 바꿀 수 있습니다.
- 스택이나 힙에 실행 권한이 있으면, 공격자가 그곳에 셸코드를 넣은 뒤 버퍼 오버플로우로 실행 흐름을 그 주소로 옮겨 셸코드를 실행할 수 있습니다.

두 번째 경우가 Return to Shellcode 공격입니다. 이 공격은 순서대로 다음과 같이 진행됩니다.

1. 스택에 있는 버퍼(`buf`)에 셸코드를 입력합니다.
2. 버퍼 오버플로우로 반환 주소를 `buf`의 주소로 덮습니다.
3. 함수가 `ret`으로 반환할 때 `buf`로 이동해서 셸코드가 실행됩니다.

마지막 단계가 성공하려면 셸코드가 들어 있는 스택에 실행 권한이 있어야 합니다. 그런데 스택은 지역 변수 같은 데이터를 저장하는 곳이라서 원래 실행 권한이 필요하지 않습니다.

그래서 데이터가 저장되는 페이지에서는 명령어를 실행하지 못하게 막는데, 이 보호 기법이 NX입니다.

![NX가 없을 때와 적용됐을 때의 Return to Shellcode](assets/posts/2026-11-12-nx/shellcode-nx.png)

NX가 적용되어도 셸코드를 입력하고 반환 주소를 덮는 것까지는 그대로 할 수 있습니다. 하지만 `ret`으로 `buf`에 도착했을 때 CPU가 그곳의 명령어를 실행하지 않기 때문에 셸코드는 실행되지 않습니다.

## NX가 적용되는 과정

NX는 순서대로 다음 과정을 거쳐 적용됩니다.

![NX가 적용되는 과정](assets/posts/2026-11-12-nx/nx-pipeline.png)

1. 컴파일·링크 과정에서 실행 파일이 요구하는 메모리 권한이 ELF 프로그램 헤더에 기록됩니다. 스택의 권한은 `GNU_STACK` 항목에 기록됩니다.
2. 프로그램을 실행하면 커널의 ELF 로더가 이 정보를 바탕으로 각 페이지의 권한을 설정합니다.
3. CPU는 페이지의 NX 비트를 확인해, 실행 권한이 없는 페이지에서는 명령어가 실행되지 않도록 차단합니다.

즉, 필요한 권한은 링크할 때 파일에 기록되고, 실제 메모리 권한은 프로그램을 메모리에 적재할 때 설정됩니다.

## 직접 확인해 보기

> [!info] 실습 환경
> Ubuntu 24.04 (WSL2, x86_64), gcc 13.3.0, glibc 2.39, gdb 15.1 + pwndbg

Dreamhack의 예제 코드를 직접 컴파일하고 실행해 보았습니다.

```c
// Name: nx.c

#include <stdio.h>

int main(void) {
    unsigned char code[] = {
        0x90,  // nop
        0xc3   // ret
    };

    void (*run)(void) = (void (*)(void))code;

    printf("code address: %p\n", code);
    run();

    puts("code executed");
    return 0;
}
```
_출처: [Dreamhack](https://dreamhack.io/)_

위 코드는 순서대로 다음을 실행합니다.

1. 스택에 있는 `code` 배열에 `nop`(0x90)과 `ret`(0xc3) 명령어 2바이트를 넣습니다.
2. `code`의 주소를 출력합니다.
3. `code`의 주소를 함수처럼 호출합니다.
4. 호출에서 돌아오면 `code executed`를 출력합니다.

스택에 넣은 데이터를 명령어로 실행하는 상황을 가장 단순하게 만든 코드입니다. 스택에 실행 권한이 있으면 4번까지 실행되고, 실행 권한이 없으면 3번에서 프로그램이 종료됩니다.

### 컴파일

같은 코드를 두 가지 옵션으로 컴파일했습니다.

- `nx_disabled`: `-Wl,-z,execstack` 옵션으로 스택에 실행 권한을 주었습니다.
- `nx_enabled`: `-Wl,-z,noexecstack` 옵션으로 스택에 실행 권한을 주지 않았습니다.

Ubuntu의 gcc는 옵션을 주지 않아도 NX가 기본으로 적용됩니다.

![두 가지 옵션으로 컴파일한 뒤 GNU_STACK 확인](assets/posts/2026-11-12-nx/nx-compile.png)

`readelf -lW`로 프로그램 헤더를 보면 스택의 권한이 기록된 `GNU_STACK` 항목이 있습니다. `nx_disabled`는 `RWE`, `nx_enabled`는 `RW`입니다.

같은 코드인데 실행 권한을 뜻하는 `E` 한 글자만 다릅니다. 앞에서 설명한 것처럼 스택의 권한이 링크할 때 파일에 기록된 것입니다.

### checksec으로 확인하기

checksec은 ELF 파일에 기록된 정보를 읽어서 어떤 보호 기법이 적용되었는지 보여 주는 도구입니다. pwndbg의 `checksec` 명령으로 두 파일을 확인했습니다.

![checksec 결과](assets/posts/2026-11-12-nx/nx-checksec.png)

Canary, RELRO, PIE 같은 다른 항목은 이번 실습과 관련이 없으니 NX 항목만 보면 됩니다.

`nx_enabled`는 `NX enabled`로 나옵니다.

`nx_disabled`는 NX 항목이 `NX unknown`으로 나오고, 그 아래에 `Stack: Executable`과 `RWX: Has RWX segments`가 추가로 표시됩니다. 스택에 실행 권한이 있다는 뜻입니다. `GNU_STACK missing`이라는 문구가 붙어 있지만, 위에서 확인한 것처럼 `GNU_STACK` 항목은 있고 실행 권한이 켜져 있는 상태입니다.

### 실행해 보기

![nx_disabled와 nx_enabled 실행 결과](assets/posts/2026-11-12-nx/nx-run.png)

`nx_disabled`는 스택에 실행 권한이 있기 때문에 `nop; ret`이 실행되고, `main`으로 돌아와 `code executed`가 출력됩니다.

반면 `nx_enabled`는 `code`의 주소까지는 출력되지만, 그 주소의 명령어를 실행하려는 순간 `Segmentation fault`가 발생하고 종료됩니다. 참고로 `code`의 주소는 실행할 때마다 달라집니다.

여기서 주의할 점이 있습니다. `Segmentation fault`는 존재하지 않는 주소에 접근할 때만 발생하는 것이 아닙니다. 존재하는 주소라도 읽기·쓰기·실행에 필요한 권한이 없으면 발생합니다.

그래서 `Segmentation fault`가 발생했다는 것만으로 NX가 원인이라고 단정할 수는 없습니다. 실행하려던 주소와 그 영역의 권한을 함께 확인해야 합니다.

### gdb로 확인하기

`nx_enabled`를 gdb에서 `run`으로 실행해서 어느 주소에서 멈추는지 확인했습니다. `vmmap`은 프로세스의 메모리 영역과 권한을 보여 주는 pwndbg 명령입니다.

![nx_enabled가 멈춘 위치와 그 영역의 권한](assets/posts/2026-11-12-nx/nx-gdb-enabled.png)

화면에서 확인할 수 있는 것은 다음 세 가지입니다.

1. 출력된 `code`의 주소가 `0x7fffffffd716`인데, `SIGSEGV`가 발생한 주소도 똑같이 `0x7fffffffd716`입니다.
2. `x/i $rip`로 보면 멈춘 곳의 명령어는 `code`에 넣어 둔 `nop`입니다.
3. `vmmap $rip`로 이 주소가 속한 영역을 보면 `[stack]`이고, 권한은 `rw-p`로 실행 권한이 없습니다. (마지막 `p`는 권한이 아니라 다른 프로세스와 공유하지 않는 영역이라는 표시입니다.)

즉, 스택에 있는 `nop`을 실행하려는 순간 CPU가 실행을 막았고, 커널이 프로세스에 `SIGSEGV` 신호를 보내 종료시킨 것입니다.

이번에는 `nx_disabled`를 `start`로 `main`에서 멈춘 뒤, 같은 방법으로 스택의 권한을 확인했습니다.

![nx_disabled의 스택 권한](assets/posts/2026-11-12-nx/nx-gdb-disabled.png)

같은 `[stack]` 영역인데 권한이 `rwxp`입니다. 스택에 실행 권한이 있기 때문에 `nx_disabled`에서는 스택의 `nop; ret`이 그대로 실행된 것입니다.

## NX의 한계

NX는 스택 같은 데이터 영역에서 명령어가 실행되는 것을 막을 뿐, 버퍼 오버플로우로 반환 주소가 바뀌는 것 자체는 막지 못합니다.

그래서 공격자는 셸코드를 직접 넣어 실행하는 대신, 프로세스에 이미 존재하고 실행 권한도 있는 코드로 반환 주소를 바꾸는 방법을 사용합니다. 그중 가장 대표적인 것이 라이브러리에 있는 함수를 호출하는 Return to Library입니다.

## 정리

- NX는 스택이나 힙처럼 데이터를 저장하는 영역에서 실행 권한을 없애, 그곳에 넣은 셸코드가 실행되지 않게 하는 보호 기법입니다.
- 스택의 권한은 링크할 때 ELF 프로그램 헤더의 `GNU_STACK`에 기록되고, 프로그램을 실행할 때 커널이 그 정보대로 페이지 권한을 설정합니다.
- 실행 권한이 없는 페이지의 명령어를 실행하려고 하면 `Segmentation fault`가 발생하고 프로세스가 종료됩니다.
- NX는 반환 주소가 덮이는 것 자체는 막지 못하기 때문에, 이미 실행 권한이 있는 코드를 이용하는 Return to Library 같은 공격은 막을 수 없습니다.
