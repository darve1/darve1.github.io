## 개요

Address Space Layout Randomization(ASLR)은 프로그램을 실행할 때마다 스택, 힙, 라이브러리가 놓이는 주소를 무작위로 바꾸는 보호 기법입니다. 
PIE(Position-Independent Executable)는 실행 파일의 코드와 데이터도 무작위 주소에 올라갈 수 있도록 만든 실행 파일입니다.

ASLR과 PIE가 왜 필요한지 알아보고, 두 기법을 적용했을 때 주소가 어떻게 달라지는지 직접 확인해 봅시다.

## ASLR이 공격을 어렵게 만드는 이유

ASLR을 알아보기 전에 먼저 공격자에게 주소가 왜 필요한지 설명하겠습니다.

스택 버퍼 오버플로우로 반환 주소를 덮으면 실행 흐름을 원하는 곳으로 옮길 수 있습니다. 하지만 이 공격이 성공하려면 이동할 주소를 정확히 알아야 합니다. 스택에 넣은 셸코드를 실행하려면 스택 버퍼의 주소를 알아야 하고, NX 때문에 셸코드 대신 라이브러리 함수를 호출하는 Return to Library 공격을 하려면 libc에 있는 함수의 실제 주소를 알아야 합니다.

프로그램을 실행할 때마다 이 주소들이 같다면, 공격자는 gdb로 주소를 한 번만 확인해 두고 그 값을 그대로 공격에 쓸 수 있습니다. 반대로 반환 주소를 틀린 값으로 덮으면 엉뚱한 주소로 넘어가고, 그 주소에 코드가 없으면 Segmentation fault가 발생해 프로그램이 종료됩니다.

ASLR은 주소를 프로그램을 실행할 때마다 바꿔서, 공격자가 미리 확인해 둔 주소로는 공격이 성공하지 못하게 만듭니다.

이때 주소가 될 수 있는 경우의 수를 ASLR의 엔트로피(Entropy)라고 합니다. 경우의 수가 많을수록 엔트로피가 높다고 하고, 엔트로피가 높을수록 공격자가 주소를 찍어서 맞히기 어려워집니다. 그래서 주소 공간이 작아 경우의 수가 적은 32비트 환경에서는, 주소를 추측해 여러 번 시도하는 방법으로 공격이 성공하기도 합니다.

## ASLR 원리

ASLR은 프로그램이 실행될 때 커널이 메모리 영역의 시작 주소를 무작위로 정하는 보호 기법입니다. 리눅스에서는 스택, 힙, 그리고 libc 같은 공유 라이브러리가 올라가는 영역의 주소가 바뀝니다.

또한 ASLR은 실행 파일에 들어 있는 기능이 아니라 커널 차원에서 지원하는 보호 기법입니다. 스택 카나리, NX, PIE는 컴파일할 때 적용되어 실행 파일에 흔적이 남지만, ASLR은 실행 파일과 상관없이 시스템 설정에 따라 적용됩니다. 그래서 ASLR이 적용되었는지 확인하려면 checksec같은 실행 파일을 검사하는 도구가 아니라 /proc에 있는 시스템 설정을 확인해야 합니다.
리눅스에서는 /proc/sys/kernel/randomize_va_space 값으로 ASLR을 어디까지 적용할지 정합니다.

설정 값에 따라서

- 0: ASLR을 적용하지 않습니다.
- 1: 스택과 라이브러리 영역의 주소를 무작위로 정합니다.
- 2: 1에 더해 힙의 주소도 무작위로 정합니다.

Ubuntu는 기본값이 2입니다.

## ASLR 직접 확인해 보기

> [!info] 실습 환경
> Ubuntu 24.04 (WSL2, x86_64), gcc 13.3.0, glibc 2.39, gdb 15.1 + pwndbg

Dreamhack의 예제 코드를 직접 컴파일하고 실행해 보겠습니다.

```c
// Name: addr.c
// Compile: gcc addr.c -o addr -ldl -no-pie -fno-PIE

#include <dlfcn.h>
#include <stdio.h>
#include <stdlib.h>

int main() {
  char buf_stack[0x10];                   // 스택 버퍼
  char *buf_heap = (char *)malloc(0x10);  // 힙 버퍼

  printf("buf_stack addr: %p\n", buf_stack);
  printf("buf_heap addr: %p\n", buf_heap);
  printf("libc_base addr: %p\n",
         *(void **)dlopen("libc.so.6", RTLD_LAZY));  // 라이브러리 주소

  printf("printf addr: %p\n",
         dlsym(dlopen("libc.so.6", RTLD_LAZY),
               "printf"));  // 라이브러리 함수의 주소
  printf("main addr: %p\n\n", main);  // 코드 영역의 함수 주소
}
```
_출처: [Dreamhack](https://dreamhack.io/)_

위 코드는 순서대로 다음 주소를 출력합니다.

1. buf_stack: 스택 주소
2. buf_heap: 힙 주소
3. libc_base: libc 베이스 주소
4. printf: libc에 있는 printf 함수 주소
5. main: 코드 영역에 있는 main 함수 주소

Ubuntu의 gcc는 기본으로 PIE가 적용되어 있어서, 옵션 없이 컴파일하면 실행 파일의 주소까지 바뀝니다. 그래서 먼저 ASLR만 확인하기 위해 주석에 적힌 대로 -no-pie -fno-PIE 옵션으로 PIE를 끄고 컴파일하겠습니다.
-fno-PIE는 컴파일할 때, -no-pie는 링크할 때 PIE를 끄는 옵션입니다.

![addr를 두 번 실행한 결과](assets/posts/2026-11-26-aslr-pie/aslr-nopie-run.png)

randomize_va_space 값이 2이므로 ASLR이 켜진 상태에서 같은 프로그램을 두 번 실행했습니다. 실행 결과에서 다음과 같은 특징을 볼 수 있습니다.

PIE를 끄고 컴파일했기 때문에 main의 주소는 두 번 모두 0x4011b6으로 같습니다. 반면 buf_stack, buf_heap, libc_base, printf의 주소는 실행할 때마다 달라지는 것을 볼 수 있습니다. 이는 스택, 힙, 라이브러리에는 ASLR이 적용된 것이고, ASLR이 적용된 영역은 프로그램을 실행해 보기 전까지 실제 주소를 알 수 없음을 의미합니다.

실행을 그림으로 나타내면 다음과 같습니다.

![addr를 두 번 실행했을 때의 메모리 배치](assets/posts/2026-11-26-aslr-pie/aslr-layout.png)

ASLR은 libc 안의 함수들을 하나하나 흩어 놓는 것이 아니라, libc 전체를 통째로 다른 베이스 주소에 매핑합니다. 그래서 같은 libc 파일을 쓰는 한 libc_base와 printf 사이의 거리는 실행할 때마다 같습니다. 실제로 두 실행 결과에서 printf의 주소에서 libc_base를 빼면 모두 0x60100이 나옵니다. 0x60100이 이 실습에서의 libc의 base address로 부터 printf까지의 offset인 것입니다. 이 값은 같은 libc 파일에서는 유지되지만, libc의 버전이나 빌드가 달라지면 달라질 수 있다고 합니다.

## PIE 원리

### PIC와 상대 주소

PIE를 이해하려면 먼저 PIC를 알아야 합니다. 리눅스에서 쓰는 ELF 파일에는 실행 파일과 공유 오브젝트 등이 있습니다. addr나 pie처럼 직접 실행하는 파일은 실행 파일이고, libc.so 같은 공유 라이브러리는 공유 오브젝트입니다.

공유 라이브러리는 여러 프로그램이 함께 사용하기 때문에, 프로그램마다 그리고 실행할 때마다 다른 주소에 올라갈 수 있습니다. 이때 코드가 공유 라이브러리가 특정 주소에 올라간다고 가정하고 절대 주소로 함수나 데이터를 가리키고 있다면, 다른 주소에 올라갔을 때 엉뚱한 곳을 참조하게 됩니다.

그래서 공유 라이브러리는 어느 주소에 올라가도 동작하도록 만드는데, 이런 코드를 PIC(Position Independent Code)라고 합니다. PIC는 함수나 데이터를 가리킬 때 절대 주소 대신 명령어의 위치(rip)를 기준으로 한 상대 주소를 사용합니다.

### PIE의 역할

PIE가 아닌 실행 파일은 링크할 때 메모리의 어느 주소에 올라갈지가 정해집니다. 
x86-64에서는 보통 0x400000부터 올라가도록 만들어지고, 파일 안의 코드와 데이터도 그 주소를 기준으로 만들어집니다. 그래서 다른 주소에 올리면 주소가 맞지 않게 되므로, 커널은 이 파일을 항상 정해진 주소에 올립니다. 이 경우 공격자는 라이브러리 주소를 모르더라도 실행 파일 안에 있는 코드와 데이터의 주소는 미리 알 수 있습니다.

PIE(Position Independent Executable)는 이름에서 유추할 수 있듯이, PIC를 실행 파일에 적용한 것입니다. 원래 공유 라이브러리에 쓰던 방식을 실행 파일에도 쓴 것으로, PIE로 컴파일한 실행 파일은 특정 주소에 올라간다고 가정하지 않고 실행할 때 로더가 정한 시작 주소를 기준으로 동작합니다.

그래서 PIE 실행 파일 안에 적힌 주소는 실제 주소가 아니라, 파일이 올라간 시작 주소(PIE base)로부터의 거리(오프셋)입니다. 실행할 때 시작 주소가 정해지면 실제 주소는 다음과 같이 계산됩니다.

```text
실제 주소 = PIE base + 오프셋
```

PIE는 실행파일을 고정된 주소에 적재하지 않아도 되게 만들고, 실제로 무작위로 정하는 것은 ASLR입니다. 그래서 ASLR이 꺼져 있으면 PIE 실행 파일도 매번 같은 주소에 올라갑니다.

## PIE 직접 확인해 보기


이번에는 같은 코드를 -no-pie -fno-PIE 옵션 없이 pie라는 이름으로 컴파일하고 실행해 보겠습니다.

![pie를 두 번 실행한 결과](assets/posts/2026-11-26-aslr-pie/pie-run.png)

PIE 없이 컴파일한 addr는 몇 번을 실행해도 main의 주소가 0x4011b6으로 같았지만, pie는 main의 주소도 0x5f55b30791c9, 0x5a1e67e091c9로 실행할 때마다 달라지는 것을 볼 수 있습니다. 즉, **PIE로 컴파일하면 실행 파일의 코드 영역도 ASLR에 의해 실행할 때마다 다른 주소에 올라갑니다.**

그런데 main 주소의 끝 세 자리는 두 번 모두 1c9로 같습니다. 이는 실행 파일의 시작 주소만 바뀌고 오프셋은 그대로라는 것을 의미합니다.

![pie를 두 번 실행했을 때의 메모리 배치](assets/posts/2026-11-26-aslr-pie/pie-layout.png)

### 파일에 적힌 주소 비교

readelf와 nm으로 두 실행 파일을 비교해 보겠습니다.

![두 실행 파일의 형식과 main 주소](assets/posts/2026-11-26-aslr-pie/pie-readelf.png)

readelf -h로 ELF 헤더를 보면 addr의 형식은 EXEC, pie는 DYN인 것을 볼 수 있습니다. DYN은 원래 공유 라이브러리가 쓰는 형식인데, PIE 실행 파일도 이 형식을 씁니다.

nm으로 main의 주소를 보면 addr에는 실행했을 때 출력된 주소인 0x4011b6이 그대로 적혀 있지만, pie에는 0x11c9라는 오프셋만 적혀 있습니다. 
main의 주소는 실행할 때마다 무작위로 바뀌지만, 끝 세 자리가 항상 1c9였던 것은 이 오프셋 때문입니다.

### checksec 비교

pwndbg의 checksec으로 두 파일을 확인해 보겠습니다.

![checksec 결과](assets/posts/2026-11-26-aslr-pie/pie-checksec.png)

PIE 항목을 보면 addr는 No PIE (0x400000)으로 0x400000에 고정되어 올라가고, pie는 PIE enabled로 PIE가 적용된 것을 볼 수 있습니다.

그리고 checksec 결과에는 ASLR 항목이 없습니다. 앞에서 설명한 것처럼 ASLR은 실행 파일이 아니라 커널이 적용하는 보호 기법이기 때문에, 실행 파일만 보고는 ASLR이 켜져 있는지 알 수 없습니다.

## 공격 관점의 변화

PIE가 적용되지 않은 실행 파일은 항상 같은 주소에 올라가기 때문에, 공격자는 실행 파일 안에 있는 함수나 문자열의 주소를 미리 확인해 두고 공격 코드에 그대로 넣을 수 있습니다. NX 글에서 이야기한 Return to Library 같은 공격도, 실행 파일이 PIE가 아니라면 실행 파일 안에 있는 주소는 따로 구할 필요 없이 바로 사용할 수 있습니다.

반면 PIE가 적용되면 실행 파일 안의 코드와 데이터 주소도 실행할 때마다 바뀌기 때문에, 미리 확인해 둔 주소를 그대로 쓸 수 없습니다. 따라서 PIE가 적용된 실행 파일을 공격하려면 지금 실행 중인 프로세스에서 실제 코드 주소를 알아내야 합니다.

## ASLR과 PIE의 한계

ASLR과 PIE가 바꾸는 것은 각 영역의 시작 주소뿐이고, 영역 안에서의 위치(오프셋)는 그대로입니다. 여기서 영역은 스택, 힙, libc, 실행 파일처럼 메모리에 따로 올라가는 부분이고, 오프셋은 영역의 시작 주소에서 얼마나 떨어져 있는지를 나타냅니다.

앞에서 pie를 두 번 실행한 결과를 다시 보면, libc 베이스 주소는 실행할 때마다 바뀌었지만 printf는 두 번 모두 libc 베이스 주소에서 0x60100만큼 떨어진 곳에 있습니다.

```text
               libc 베이스 주소   printf 주소
첫 번째 실행   0x7e9027e00000     0x7e9027e60100
두 번째 실행   0x7cb22ae00000     0x7cb22ae60100
```

main도 마찬가지로 PIE base는 바뀌었지만, 두 번 모두 PIE base에서 0x11c9만큼 떨어진 곳에 있습니다.

그래서 주소 정보가 한 번 유출되면, 공격자는 주소를 추측할 필요 없이 실제 주소를 계산할 수 있습니다. 영역 안의 주소를 하나라도 알아내면 시작 주소를 구할 수 있고, 시작 주소를 알면 그 영역에 있는 다른 주소도 모두 구할 수 있기 때문입니다.

## 세줄 요약

- ASLR은 실행할 때마다 스택, 힙, 라이브러리 주소를 무작위로 바꾸는 커널 보호 기법임.
- PIE로 컴파일해야 실행 파일 주소도 바뀌고, 아니면 0x400000에 고정됨.
- 바뀌는 건 시작 주소뿐이라, 그 실행에서 주소 하나만 유출돼도 나머지를 계산할 수 있음.
